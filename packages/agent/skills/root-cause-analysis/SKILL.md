# 结构化根因分析

你正在帮助用户定位一个故障的**根本原因**，而不是打补丁掩盖症状。严格按下面的步骤推进，每一步都要有依据，不要跳过定位直接猜测修复。

## 步骤

1. **明确症状**：用一句话复述可观察到的错误行为——它在什么条件下发生、期望是什么、实际是什么。缺关键信息（复现步骤、报错原文、环境）时先向用户索取，不要假设。

2. **确认可复现**：确定触发条件。能稳定复现的，记下最小复现路径；只是偶发的，记录已知的触发线索，并明确指出不确定性。

3. **定位到代码/数据**：把症状收敛到具体的模块、函数或数据，说明证据链——为什么是这里，而不是别处。避免「可能在 X 也可能在 Y」的含糊结论，用证据排除。

4. **逐层追问「为什么」**：从定位点出发，连续追问「为什么会这样」，直到到达一个再往上就属于外部约束或设计前提的层级。每一层都要写出因果链条，不要一步跳到结论。

5. **区分根因与表象**：明确指出哪个是根因、哪些只是它的下游表现。修复根因后，那些表象应当一并消失——如果不能，说明还有未找到的原因。

6. **给出针对根因的修复**：提出直接作用于根因的改动，并说明为什么它不会只是掩盖症状。若根因涉及取舍（性能/兼容/工期），列出取舍而不是替用户拍板。

7. **提出验证方式**：给出能证明修复有效的具体手段——优先可复现的回归测试或可观察的行为变化，而不是「应该好了」。

## 原则

- 先证据后结论：每一步的判断都要能指向具体的日志、代码行或数据。
- 不确定就说不确定，并说明还需要什么信息才能确定，绝不用猜测冒充定位。
- 只在根因上动刀，不顺手改无关代码。
