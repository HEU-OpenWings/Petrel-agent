# 技术文档

面向开发者的**长期有效**文档：系统怎么搭的、某个子系统为什么这么设计、接口契约是什么。

与 `docs/` 下其他目录的分工：

| 目录 | 内容 | 时效 |
| --- | --- | --- |
| `docs/tech/`（本目录） | 架构说明、子系统设计与策略、接口契约 | 长期，跟着代码演进 |
| `docs/superpowers/specs/` | 单个需求的设计稿（一需求一份，带日期） | 一次性，做完即冻结 |
| `docs/superpowers/plans/` | 单个需求的实施计划与任务拆分 | 一次性，做完即冻结 |
| `docs/backend-plan.md`、`docs/frontend-plan.md` | v0.4 → v0.5 重构的路线图与组件处置清单 | 重构期间 |
| `docs/prd/` | 产品需求（**不进 git**，见 `.gitignore`） | — |

## 现有文档

- [架构说明](architecture.md) — 部署拓扑、代码分层、依赖方向、关键链路
- [上下文压缩策略](context-compaction.md) — 阈值、守卫、互斥、可见性与调参

## 约定

- 中文书写。代码标识符、文件路径、环境变量名保持原文。
- **写清「为什么」**。「是什么」读代码更快，「为什么这样而不那样」只有文档能留住。
- 引用具体文件路径（如 `apps/server/src/services/harness-registry.ts`），别只写模块名——
  路径能点开，模块名要靠猜。
- 与代码冲突时以代码为准，同时**改文档**。发现文档过期就地修掉，不要另起一份新的。
- 踩坑记录归 `CLAUDE.md` 的「踩过的坑」，不重复写在这里；本目录讲设计，那里讲陷阱。
